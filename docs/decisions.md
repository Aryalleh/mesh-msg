# Key Decisions

| # | Decision | Alternatives considered | Why |
|---|---|---|---|
| D1 | Own protocol, ideas borrowed from Reticulum/LXMF | Build directly on Reticulum; Meshtastic firmware | Tier 0 phone mesh, regional relays and shutdown UX are core; we need a compact LoRa format. Revisit if Reticulum interop becomes valuable. |
| D2 | Single packet format across all tiers | Per-tier formats with translation | No component must decrypt/re-encode; fewer trust points. |
| D3 | Noise K / X for E2E | Custom ECIES; Signal Double Ratchet | Standard, analysed; 48 B overhead fits LoRa; ratchet headers too big for 255 B frames. |
| D4 | Firmware in C++/PlatformIO + RadioLib | Rust embedded; fork Meshtastic | Widest board support (ESP32 + nRF52), mature SX1262 driver. |
| D5 | Android: Kotlin UI + transports, Go core via gomobile; no Play Services | Pure Kotlin core; Flutter/React Native; Google Nearby | One core shared with server/desktop/sim (supersedes the earlier pure-Kotlin core); Kotlin still owns BLE/Wi-Fi Direct/foreground service; must work on sideloaded, de-Googled phones. |
| D6 | Go for core, server and desktop | Kotlin/Ktor; Rust | Single static binaries, trivial cross-compile to Linux/Windows/macOS, gomobile for Android, strong censorship-circumvention ecosystem. Leaves only firmware as a second implementation. |
| D7 | Monorepo | Separate repos | Spec, vectors and implementations change together. |
| D8 | Regional relays + global federation joined by volunteer bridges | Only foreign relays reached via VPN | A country's domestic network often survives an international blackout; in-region relays connect everyone on it, and only a few bridges need a way out. |
| D9 | Relay federation = full replication (v1) | DHT / selective routing | Small text volume; maximises survival when relays are blocked or seized. Selective sync in v2. |
| D11 | LoRa is broadcast-only (managed flood, dedup, SNR-ordered rebroadcast); LoRa gateways move packets relay ↔ air | Next-hop unicast routing with hop ACKs | Matches the medium (every transmission is heard by all in range), no route state to go stale, and lets LoRa bridge relays that can't reach each other. Cost: airtime, handled by strict priority selection. |
| D10 | Desktop: Linux first, daemon + CLI + localhost web UI | Native GUI per OS | Linux is easiest to run as a service for gateway/bridge operators; web UI covers all three OSes without a GUI toolkit. |
| D12 | Direct IP links: candidate exchange + authenticated connectivity checks + UDP hole punching; path chosen by tested reachability, local first; no TURN, relays never carry a direct session | ICE with TURN fallback; choosing by address class (private = local) | Topology is arbitrary (CGNAT, hotspots, nested NAT); address class proves nothing. A relay carrying sessions would be a bandwidth and surveillance target. Cost: no direct session when both sides are behind symmetric NAT. See connectivity.md. |
| D13 | Media in two classes: normal = direct paths only; important = also through relays, delivered to offline receivers, daily allowance per account | All media through relays; no media on relays at all | Relay storage and bandwidth go to what must arrive; everything else costs relays nothing. Cost: normal media needs both sides online at once. See protocol.md §6b, server.md §6a. |
| D14 | Important-media abuse control = account age + growing proof-of-work + a public, signed, grow-only usage ledger shared by all relays (reported to and served by origin relays, also gossiped peer to peer) | Per-relay counting only; vouching by contacts; a blockchain with consensus | Each entry is signed by the uploading account, so no relay can fake usage and nobody must be trusted; counters only add up, so no consensus or mining is needed; origin relays are meeting points, not authorities. Vouching would expose the social graph. Cost: the ledger shows how many important files an account sent per day. |
| D15 | Voice calls: signaling as E2E messages (content type 7) over any path; audio only over direct links, Noise KK per call, Opus 6–24 kbps; no relay audio, no TURN | WebRTC stack with TURN; audio through relays | Keeps relays cheap and blind; reuses the core's crypto and paths; WebRTC would drag in a large stack and DTLS/SRTP identities separate from ours. Cost: no call without a direct path, and each side sees the other's IP. |
| D16 | Calls are built as streams from the start (caps per stream, stream id in every frame, fragmentation, UPDATE/CONTROL ops, shared bandwidth estimator); v1 ships audio only | Audio-only format now, new protocol for video later | Video (or screen sharing) can be added without breaking v1 clients: unknown streams, ops and codecs are ignored and the call falls back to voice. Cost: a few header bytes per audio frame. |
| D17 | All non-relayed ways to a direct path are built into the apps (IPv6 first, PCP/NAT-PMP/UPnP mapping, NAT-type detection, sequential and birthday port prediction); any relay (private or official) may offer TURN, only to its own admins, off by default | TURN for everyone; no TURN at all | Relays never carry ordinary users' calls (cost, metadata), while the people who run relays always have a path among themselves. Cost: two ordinary users both behind symmetric carrier NAT may still fail to connect. |
